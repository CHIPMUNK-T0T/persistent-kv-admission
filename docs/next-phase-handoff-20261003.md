# 次のClaudeへの引継ぎ：独立workloadでの確認を計画する

2026-10-03。最新の根拠は[三つの確認](matched-horizon-checks-findings.md)と[研究の現在地](research-status.md)。これは研究方針と次の依頼範囲を整理する文書であり、新しい実験の事前登録ではない。既存の登録・結果・判定は変更しない。

## 目的と、今回までに具体化したこと

目的は[ルール](../RULES.md)のとおり、有限容量のpersistent KV tierで、将来再利用価値の高いstateを選んで回避prefillを増やすことである。L1 victimを受けるL2に将来情報を与える比較では大きな改善余地があり、今回の凍結rankerとの比較ではresident選択の改善が大きい。

現在は「容量に合うbitだけを当てれば解ける」ではなく、**再利用の時間範囲、class内の選択規則、退去候補の適格性を組み合わせたときの効用**が中心である。all16ではclass内の学習順序がrecencyに8/12で全seed負け、leaf16では11/12で全seed勝つ。all16で両class内を無作為に選ぶとrecencyに12/12で全seed負けるため、bit単独の十分性ではない。

主要な読みはtrace末尾600秒だけには依存しない。ただしclass介入の`R ≥ 0.9`はfullの10/12からheadの9/12へ変わる。all16からh*を持ち越したleaf16では同じ10/12でR基準を満たすが、bit＋recencyのS基準は9/12にとどまる。機構間で比較器と分母が変わるので、Sの増加と絶対効用の低下を混同しない。

非再利用classとは「h以内に再利用されない」であり、永久に不要ではない。all16の損がそのclassへの学習順序の介入で現れる理由、leaf16で順序の優劣が逆転する理由は未解決である。現在のcounterだけから、内部node退去やorphaningが原因と断定しない。Mooncake内で新しい原因候補を際限なく追加することを次の主作業にはしない。

## 次に依頼する作業と停止点

**まずBailianの入力・変換監査と、独立workload確認の事前登録案を作成し、計画だけをlocal commitする。** 実装・smoke・本実行・新規fitは、この依頼には含めない。計画はレビューできる粒度まで完成させ、未決事項を列挙して報告する。pushは別の明示指示がある場合に限る。

### 1. 入力と評価対象を確定する

- 既存のTo-C / To-B / thinking / coder変換とmanifestを確認し、元データ・変換結果・loaderの識別情報を記録する。既に行ったtraceの試読・集計と、新たな結果閲覧を区別する。
- 元timestampの単位、変換後の単位、同時刻requestの順序と相互hit禁止、hashのprefix意味、partial block、capacity課金を確認する。既存の[変換script](../scripts/convert_bailian_trace.py)を出発点とし、raw traceを変更しない。
- 16-token粒度から512-tokenへまとめることで、表現可能な共有prefix・stateサイズ・capacity百分率の分母が変わる。512を主解析にする場合はその限定を明記し、元の16-token粒度で何を確認すれば変換由来かを区別できるか、最小限の対照を計画する。粒度を比較する対照では同じ絶対byte予算の比較を含め、粒度ごとに予算まで変えて効果を混ぜない。
- 原則4 traceすべてを候補にし、除外条件は結果を見る前に固定する。compulsory部分・利用可能な再利用量・L1/L2容量を報告する。新しいworkload familyであって、4つの独立deploymentとは扱わない。

この監査ではschema・識別子・件数・変換の整合性を確認し、policy utilityや最良horizonを先に読まない。追加の再利用特性を事前に見る必要があるなら、その項目と用途を先に書いて探索と区別する。

### 2. 独立確認を二つの問いに分ける

**主解析A：事前固定した条件の移植。** Mooncakeで使ったcellごとのh*（L1 0.25%×1:60、0.25%×4:150、1%×1:150、1%×4:600、2%×1:300、2%×4:600秒）と既存の容量比を移植したとき、exact bit＋recencyの効用が、各機構内のgreedy exact next-use比較器にどれだけ届くかを測る。これはこの対応表の移植試験であり、容量からhorizonを求める一般則の検証ではない。

同じ容量百分率でも絶対容量や到着量は異なるため、同じ秒数が通用することを当然とはしない。Aの不成立だけを、外部workloadでも再利用classが有用かという問い全体の否定や、後続fitの自動中止条件にはしない。

**副解析B：固定grid内での存在。** 共通gridを実行前に確定し、その中に比較器へ届くhorizonがあるかを調べる。候補は既存範囲の `{6, 15, 60, 150, 300, 600}` 秒とし、計画時点で必要性・費用を検討して最終固定する。全点を報告し、最良点は事後選択と明記する。主解析Aが外れてBだけ届いた場合は「再調整すれば届く」であり、「事前にhを選べた」とは扱わない。範囲内で届かなくても、範囲外のhorizonや他の選択規則の不可能性は主張しない。

両解析ともall16とleaf16を別に評価し、各機構内の同じ予算・label定義・admission/tie-break条件の参照を用いる。all16の比較器をleaf16の分母に流用しない。実行後に都合のよい機構・traceだけを主解析へ昇格させない。

### 3. 学習モデルを使わない確認と、モデル移植を分ける

最初の確認は、汎用baselineと将来情報を与える対照を中心にし、新しいpredictorをfitしない。exact bit＋recency、同じbit＋class内の無作為順序、greedy exact next-use、同じ機構のLRUなど、何の差を測るために必要かを明示してarmを選ぶ。従来のheap汎用baselineも絶対効用の文脈として位置づける。

「resident選択側に差がある」「学習順序の優劣が機構で逆転する」をBailianでも調べるには、比較する学習scoreが必要である。既存Mooncakeモデルを凍結して使う場合は、**同モデルの外部workloadへの移植診断**として副解析を分離する。係数・正規化・特徴計算を固定し、複数モデルを結果から選ばない。移植の失敗を「履歴では学べない」「将来情報が役立たない」と読まない。新しいfitが必要な設計なら今回に混ぜず、後続⑤へ送る。実行費用が大きければモデル移植の副解析自体を後続に回す。

### 4. 分母・窓・判定を実行前に固定する

- 主指標は追加回避prefill tokensとinput-token points。S/Rなどの比率は定義、機構、参照policyを併記し、絶対Uを必ず載せる。分母がゼロ・非正・小さい場合の扱いも事前に書く。
- 共通の評価窓を使う。labelを観測できるようmax horizon分の未来を入力に残し、末尾を除く窓と元のfull窓の役割を固定する。horizonごとに窓を変えたり、入力を切って未来label自体を変えたりしない。
- 既存の90%基準を使う場合も、成立数・不成立数・分母・seed別の符号・絶対差を報告する。5 seedはsampling変動であり、workload数を増やすものではない。
- hやmodelをcalibration期間から選ぶ案は、固定移植とgrid内の事後存在とは別の検証とする。行うなら時間分割とlabelのembargoを事前固定し、testで選び直さない。今回に必要かを計画で判断する。
- 「移植条件で届く」「gridを選び直すと届く」「試した範囲では届かない」を区別して読みを先に記す。全セル成功や順序の逆転を既定の結果にしない。
- arm×trace×cell×seed×粒度の件数表、重複する参照の再利用、必要なreproduction/closure/accounting検査、smoke条件、推定資源量、実行の停止条件を記す。新結果を見てからplan本文を変更しない。

### 5. 今回の納品物

1. 入力・変換監査の短い文書。未検証点と外的妥当性の範囲を含む。
2. 主解析と副解析、結果の読み、計算量、integrity checksを固定した事前登録案。
3. 履歴fitを今回に混ぜない理由と、後続へ残す判断を数行で記す。
4. 計画だけのlocal commit hashと差分。レビュー後の次工程は、実装・必要なテスト・コードcommit・smoke・本実行の順とする。

## 後続⑤：履歴fitへの接続点

Bailianの結果を踏まえ、**固定した適格性・予算・horizon・admission/tie-breakの下で、必要な再利用classを過去の情報から学習し、回避tokenを増やせるか**を別途事前登録する。fitと機構変更を同時に行わない。機構を選ぶ理由は対象システムの保持制約とし、学習器が勝った方を事後採用しない。

同じ特徴・モデル系列を保ったtarget比較を出発点とし、訓練/選択/評価の時間窓、labelのembargo、評価するdecision population、同じ候補での予測指標と実replayの効用を区別する。容量に合う二値fitが良くなることを前提にしない（単層Phase 0.9では改善は限定的だった）。semantic、embedding、新しい複雑なpolicy、I/O最適化は追加しない。

外部確認が不成立なら主張を適用範囲まで狭め、必要な対照を限定して再検討する。成立させるために無制限のhorizon探索やpolicy追加へ進めない。
